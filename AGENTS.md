# Working on Alien Buddies

Two assistants share this repo (OpenCode on Tyler's PC, Claude in its cloud workspace), and the
game deploys itself: **pushing `main` publishes alienbuddies.space**. Read `CLAUDE.md` first — it is
the deep guide (file map 34–82, saves, gotchas, device rules). This file is the rulebook that keeps
two editors safely on one repo.

## The handshake

- **Pull before you start:** `git pull --ff-only origin main`.
- **Push before you stop.** Unpushed work is invisible to the other assistant.
- **One editor at a time.** Reading and testing alongside is fine; do not rewrite files someone
  else is mid-way through.
- **Big or risky work goes on a branch** (`git switch -c <name>`), merged into `main` only when it
  is proven. Recent branches: `chloe-buddy`, `music-toolkit`.
- **If a push is refused**, the other assistant pushed first. Pull, rebase, merge by hand. Never
  force-push, never rewrite pushed history, never delete a release tag.

## Where knowledge lives

| Place | Who can read it |
|---|---|
| `CLAUDE.md`, `CHANGELOG.md`, commit messages, tags | both assistants — **the shared memory** |
| `AGENTS.md` (this file) | OpenCode (and any agent that reads AGENTS.md) |
| `~/knowledge-vault` on Tyler's PC | OpenCode only — Claude cannot see it |

So: anything the next assistant must know goes in `CLAUDE.md` / `CHANGELOG.md`, not only in the vault.

## CURRENT STATE block

The top of `CLAUDE.md` holds a block between `<!-- ship:auto:start -->` and `<!-- ship:auto:end -->`.
`tools/ship.mjs` rewrites its version/date/summary lines on every ship. Keep the
**In flight / next** and **Off limits** lines under it truthful — they are the first thing the next
assistant reads.

## Shipping (the only way)

1. Finish the change and play it in a browser.
2. Bump `GAME_VERSION` in `js/01-constants.js` by exactly one patch (0.2.231 → 0.2.232).
3. Add `## v<version> - YYYY-MM-DD HH:MM` at the top of `CHANGELOG.md`, written for players (plain
   words, no code names), with at least one line under it.
4. Run **`node tools/ship.mjs`**. It refuses to ship unless:
   - you are on `main` and not behind `origin/main`,
   - the version is exactly one patch up and not already tagged,
   - the newest changelog entry is that version,
   - every `js/*.js` parses and `index.html` loads `00-bootstrap.js` first,
   - `v0.1/` is untouched.
   Then it updates the CURRENT STATE block, commits `v<version>: <first changelog line>`, tags
   `v<version>`, pushes branch + tag, and waits for the live site to serve the version.
   `--dry` = checks only · `--no-live` = skip the wait · `--zip <path>` = backup zip.
5. Report the version, commit, tag and live status.

Never push by hand. Never reuse a version number. Pushing is deploying.

## Rolling back

- **Fastest:** Netlify → Deploys → pick the last good deploy → **Publish deploy**. Live in seconds,
  no code involved.
- **Code:** `git revert <hash>` (one bad build) or restore a single file with
  `git checkout <commit> -- <path>`, then ship normally.
- Every build from **v0.2.232** on is tagged, so `git tag --sort=-v:refname` lists the good points.
- **Code rollback does not touch player saves.** Saves live in each browser's `localStorage`; if a
  build writes bad save data, a rollback will not undo it.

## Never

- Touch `v0.1/` (frozen), renumber game files, or add a `<script>` out of load order.
- Hand-edit `js/74-vault-prices.js` — it is generated by `python3 tools/vault_prices.py`.
- Commit secrets, API keys or tokens.
- Ship without the version bump and changelog entry.
